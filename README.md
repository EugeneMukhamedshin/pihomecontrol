# pihomecontrol

Домашняя автоматика на Raspberry Pi 4: отопление, удалённое включение насоса и бойлера.

## Что делает

- читает 5 датчиков DS18B20 (1-Wire) и держит температуру в комнате гистерезисом;
- управляет мощностью котла серво-сигналом (GPIO22);
- **включает и выключает три контактора через один API `switch`:** пускатель
  котла (GPIO27, обратная связь GPIO17), насос (GPIO23) и бойлер (GPIO24);
- отдаёт веб-интерфейс на порту 80 и метрики Prometheus на 9000;
- пускает в интерфейс по паролю: страница и сокет закрыты, пока не выполнен вход;
- пишет суточные CSV в `data/`.

У насоса и бойлера своя автоматика (реле давления, термостат) — здесь только питание.
Котлом управляет гистерезис, но ручная кнопка в интерфейсе тоже идёт через `switch`.
Есть защита от частых переключений, сохранение состояния между перезапусками
и аварийное выключение при остановке сервиса.

## Железо

| GPIO | Назначение | Режим |
|---|---|---|
| 17 | Обратная связь пускателя котла | вход |
| 22 | Мощность котла (серво) | выход |
| 27 | Реле «нагрев» | выход |
| 23 | Контактор насоса | выход |
| 24 | Контактор бойлера | выход |
| 4 | Шина 1-Wire | — |

Реле подключаются только через модуль с оптопарой и отдельным питанием.
GPIO Raspberry Pi — 3,3 В и единицы миллиампер, катушку контактора напрямую не подключать.

## Запуск на Raspberry Pi

Для разовой проверки достаточно:

```bash
npm install
sudo node homecontrol.js      # порт 80 требует root, либо поставьте PORT=8080
```

Для постоянной работы лучше поставить systemd-сервис: он поднимает приложение
после перезагрузки, перезапускает при падении и даёт право на порт 80 без root.
pm2 для этого не нужен.

### Установка сервиса (заменяет pm2)

Сначала остановите старую версию под pm2, иначе она займёт порт 80:

```bash
pm2 list
pm2 stop <имя-приложения>
pm2 delete <имя-приложения>
pm2 save
```

Если pm2 запускали через `sudo`, те же команды тоже выполняйте через `sudo`
(у root и у `pi` свои списки процессов).

Если pm2 больше ничего не запускает, уберите его из автозагрузки:
`pm2 unstartup && pm2 kill`. Если под pm2 остались другие приложения, оставьте
его — конфликтовать будет только порт.

Теперь обновите код и поставьте сервис (из каталога проекта на Pi):

```bash
git pull                    # если меняли config.txt: git pull --autostash
sudo bash tools/install-service.sh
```

Скрипт проверит Node.js и `pigpiod`, создаст `config/pihomecontrol.env` из
примера, поставит зависимости (`npm ci`), установит
`/etc/systemd/system/pihomecontrol.service`, включит автозапуск и запустит
сервис. Повторный запуск безопасен — так обновляют юнит после изменений;
если зависимости не менялись, можно добавить `--no-install`.

Настройки сервиса — в `config/pihomecontrol.env` (порт, `AUTH_PASSWORD`,
`AUTH_SECRET`, `AUTH_COOKIE_SECURE`); файл в git не попадает. `config.txt`,
`devices.json`, `auth.json` и `state.json` лежат в каталоге приложения и при
деплое не перезаписываются.

Проверка и логи:

```bash
systemctl status pihomecontrol
journalctl -u pihomecontrol -f       # stdout и пароль при первом запуске
tail -f homecontrol.log              # собственный лог приложения
```

### Деплой одной командой

С Windows (PowerShell, нужен OpenSSH-клиент):

```powershell
.\deploy\deploy.ps1 -Target pi@192.168.1.50
```

Скрипт заходит на Pi, делает `git pull`, `npm ci`, перезапускает сервис и
проверяет, что `/login` отвечает. Пароль sudo спросит в терминале; если
PowerShell запрещает скрипты, запустите
`powershell -ExecutionPolicy Bypass -File .\deploy\deploy.ps1 -Target ...`.
Изменения должны быть закоммичены и запушены в `origin` — `git pull` берёт
именно оттуда. Если зависимости не менялись — `-NoInstall`, если код уже
скопирован вручную — `-NoPull`.

На самом Pi то же самое:

```bash
bash tools/deploy.sh
```

`config.txt` приложение меняет во время работы, поэтому деплой использует
`git pull --autostash` и не теряет уставки. Если upstream тоже изменил этот
файл, скрипт остановится и покажет конфликт — его нужно разрешить вручную.

Откат на предыдущую версию:

```bash
git log --oneline -5
git checkout <commit>
bash tools/deploy.sh --no-pull
```

### Переменные окружения

При запуске через systemd переменные берутся из `config/pihomecontrol.env`
(пример — `config/pihomecontrol.env.example`).

- `PORT` — порт веб-интерфейса (по умолчанию 80);
- `METRICS_PORT` — порт метрик Prometheus (по умолчанию 9000);
- `GPIO_MOCK=1` — заглушка GPIO, чтобы запустить интерфейс на обычном компьютере;
- `AUTH_PASSWORD` — пароль для входа (по умолчанию создаётся в `auth.json`);
- `AUTH_SECRET` — секрет подписи cookie (по умолчанию создаётся в `auth.json`);
- `AUTH_COOKIE_SECURE=1` — передавать cookie только по HTTPS (за TLS-прокси).

## Первый запуск: проверка реле

В `devices.json` по умолчанию стоит глобальный `"dryRun": true` — реальные GPIO
не управляются, интерфейс работает вхолостую. У пускателя котла стоит
`"dryRun": false`: он уже подключён и проверен. Насос и бойлер остаются
вхолостую, пока не убедитесь в полярности их реле.

1. Отсоедините 220 В от контакторов.
2. Проверьте, на каком уровне щёлкает реле:

   ```bash
   sudo node tools/relay-test.js
   sudo node tools/relay-test.js 23   # только один GPIO
   ```

   Щёлкнуло после «уровень 1» → `activeLow: false`; после «уровень 0» → `activeLow: true`.

3. Поставьте правильные `activeLow` и `"dryRun": false`, перезапустите сервис.
4. Подключите силовую часть и проверьте нажатием кнопок в интерфейсе.

## Интерфейс

Открывается с телефона, ничего устанавливать не нужно.

- сверху — текущая температура выбранного датчика и уставка: кнопки «−»/«+»
  с шагом 0,5 °C, значение можно ввести вручную;
- плитки датчиков: для управления нагревом выбираются «Гостиная» и «Кухня»,
  остальные (кессон, улица, труба) показываются только для контроля;
- «Устройства» — пускатель котла, насос и бойлер с крупными кнопками;
- мощность котла и допуски (гистерезис 0,5 °C) в интерфейс не выведены —
  они задаются в `config.txt`.

Страница не использует внешние CDN: стили встроены, socket.io отдаёт сам сервер,
поэтому работает без интернета.

## Вход в интерфейс

Страница и socket.io закрыты паролем. Внешние компоненты и база данных не нужны:
пароль и секрет подписи лежат в `auth.json` рядом с `homecontrol.js` (файл
создаётся сам и в git не попадает), а вход подтверждается HttpOnly-cookie с
HMAC-подписью. Cookie живёт 30 дней и не читается из JavaScript.

При первом запуске сервер создаёт `auth.json` и один раз печатает пароль в лог
(он же пишется в `homecontrol.log`):

```
Аутентификация включена. Пароль создан: qfy8-s5xe-ijma-qenj (сохранён в auth.json)
```

Дальше пароль берётся из `auth.json`. Задать свой можно так:

- переменной `AUTH_PASSWORD` — удобно для контейнера, на диск пароль не пишется;
- полем `"password"` в `auth.json` (файл с правами 600).

Если задать через окружение и пароль, и секрет (`AUTH_PASSWORD` + `AUTH_SECRET`),
`auth.json` вообще не создаётся. При старте в лог пишется, откуда взят пароль —
пароль из окружения в лог не попадает.

После смены пароля все старые входы перестают действовать: ключ подписи cookie
зависит от пароля. Кнопка «Выйти» — в правом верхнем углу страницы.

Ограничения простой схемы:

- один пароль на всех, без пользователей и ролей;
- 5 неудачных попыток с одного IP блокируют вход на минуту;
- отозвать отдельную cookie нельзя: «Выйти» стирает её в браузере, а при
  подозрении на кражу нужно сменить пароль (старые входы сразу перестанут работать);
- без HTTPS пароль и cookie идут по сети открыто: наружу — только через
  TLS-прокси (nginx/Caddy) и с `AUTH_COOKIE_SECURE=1`, а лучше в LAN/VPN;
- `/metrics` на порту 9000 не защищён и должен быть доступен только в LAN.

Если пароль забыт: остановите сервис, удалите `auth.json` и запустите снова —
сервер создаст новый пароль и напечатает его в лог.

## Настройки

`config.txt` (позиционный, через `;`): `мощность_серво;цель;нижний_дельта;верхний_дельта;индекс_датчика`.
Интерфейс меняет только цель и индекс датчика; мощность и допуски правятся
вручную (по умолчанию 2050 и 0,5/0,5).

`devices.json`:

```json
{
  "stateFile": "state.json",
  "dryRun": true,
  "devices": [
    {
      "id": "heater",
      "title": "Пускатель котла",
      "pin": 27,
      "feedbackPin": 17,
      "activeLow": false,
      "minOffSec": 30,
      "restoreOnStart": false,
      "dryRun": false
    },
    {
      "id": "pump",
      "title": "Насос (скважина)",
      "pin": 23,
      "activeLow": false,
      "feedbackPin": null,
      "minOnSec": 0,
      "minOffSec": 30,
      "restoreOnStart": true
    }
  ]
}
```

- `dryRun` — глобальный выключатель GPIO; у устройства можно переопределить
  (`heater` работает, остальные пока вхолостую);
- `activeLow` — полярность входа реле (проверяется `tools/relay-test.js`);
- `feedbackPin` — вход вспомогательного контакта контактора (`null`, если не подключён);
- `minOffSec` — минимальная пауза перед включением (насосу 30 с, чтобы не дребезжать);
- `restoreOnStart` — восстанавливать состояние после перезапуска. У котла `false`:
  после рестарта нагрев выключен, автоматика включит его по температуре.

Состояние хранится в `state.json` и в git не попадает.

## API сокета

Сокет требует cookie, полученную после входа; без неё подключение отклоняется с
`E_UNAUTHORIZED`, а запрос с чужого `Origin` — с `E_ORIGIN`.

- `switch` → `{id, on}` с подтверждением `{ok, devices}` или `{ok: false, code, message}`;
- `getDevices` → снимок состояния;
- `devices` — широковещательное обновление.

## Эксплуатация

- при `SIGINT`/`SIGTERM`/необработанном исключении все выходы гасятся;
- конфиг пишется атомарно (через `.tmp` + rename), битый файл больше не оставляет котёл без верхнего порога;
- датчики читаются с проверкой CRC; после трёх ошибок подряд значение скрывается, а нагрев выключается;
- при недостоверной температуре котёл не греет «вслепую».

## Камера: запись в Яндекс Диск

Tapo C320WS не умеет писать в чужое облако: в приложении есть только карта
microSD и платная подписка Tapo Care. Зато камера отдаёт RTSP, поэтому запись
делает Pi, а в облако её складывает rclone:

```
камера --RTSP--> ffmpeg (сегменты по 5 минут) --> rclone --> Яндекс Диск
```

Учтите ограничение самой камеры: одновременно она держит только два источника
записи из трёх — microSD, Tapo Care и RTSP. Если на камере включены карта и
Tapo Care, поток по RTSP отключается, поэтому для записи через Pi SD-карту
нужно вынуть.

### Настройка rclone

Нужен пароль приложения Яндекса, а не основной пароль:

1. <https://id.yandex.ru/security> → **Доступ к вашим данным** → **Пароли приложений**;
2. тип **«Файлы WebDAV»**, любое название (`rpi-cam`), пароль показывается один раз;
3. пароль начинает действовать **через 2-3 часа** — раньше rclone получит 401.

```bash
rclone config
#   n → имя yadisk → тип webdav → url https://webdav.yandex.ru
#   vendor other → логин Яндекса → пароль приложения
rclone lsd yadisk:        # должен показать папки
```

### Настройки и установка

```bash
cp config/camera.env.example config/camera.env
nano config/camera.env                     # RTSP-адрес, папка буфера, CAM_REMOTE
sudo apt install ffmpeg
sudo tools/cam-install.sh
```

`config/camera.env` в git не попадает: там пароль от камеры. Файл читается
через `source`, поэтому правьте его на Pi или пересохраните с переводами строк
LF: CRLF из Windows сломает значения (рекордер предупредит об этом в логе).

Что появляется в проекте:

| Файл | Назначение |
|---|---|
| `tools/cam-recorder.sh` | ffmpeg пишет сегменты по 5 минут и переподключается к камере |
| `tools/cam-upload.sh` | rclone move заливает готовые сегменты и удаляет их локально |
| `tools/cam-status.sh` | диагностика: процессы, буфер, облако, хвост логов |
| `deploy/systemd/*.service` | юниты `cam-recorder` и `cam-upload` |

### Проверка

```bash
tools/cam-status.sh
rclone lsl yadisk:cam | tail -3
```

Первый файл приедет в облако через 15-20 минут: сегмент 5 минут плюс
`CAM_MIN_AGE=10m`, чтобы не забирать недописанное. Что происходит, видно в
`data/cam-recorder.log`, `data/cam-upload.log` и `data/cam-rclone.log`.

Если rclone отвечает 401 — почти всегда пароль приложения ещё не активировался
либо выбран не тот тип пароля. Проверить, что именно запускается вместо камеры:
`tools/cam-recorder.sh --print-cmd` (пароль в выводе маскируется).

### Сколько это ест

2K-поток — примерно 2-4 Мбит/с, то есть **1-1,8 ГБ в час** и 30-45 ГБ в сутки
при непрерывной записи. Поэтому в примере стоит `CAM_RETENTION_DAYS=14`, а
облако рано или поздно придётся оплатить. Для экономии трафика поставьте
`stream2` в `CAM_RTSP_URL`. Сегменты лучше писать на USB-диск: SD-карта от
непрерывной записи умирает за месяцы.

## Локальная проверка на ПК

Проверяются интерфейс, логика гистерезиса и API контакторов — без Raspberry Pi.

1. Node.js 20. Если `node_modules` нет, ставьте зависимости без сборки native-модулей:

   ```bash
   npm install --ignore-scripts
   ```

   `onoff` и `pigpio` на ПК не нужны: в mock-режиме они не загружаются.

2. Запуск. PowerShell:

   ```powershell
   $env:GPIO_MOCK="1"
   $env:PORT="8080"
   node homecontrol.js
   ```

   bash:

   ```bash
   GPIO_MOCK=1 PORT=8080 node homecontrol.js
   ```

3. Откройте <http://localhost:8080> и войдите по паролю. При первом запуске
   сервер создаёт `auth.json` и печатает пароль в консоль:

   ```
   Аутентификация включена. Пароль создан: qfy8-s5xe-ijma-qenj (сохранён в auth.json)
   ```

   Что видно в mock-режиме:

   - жёлтая плашка «Тестовый режим: GPIO не управляются»;
   - температуры-заглушки: 26,4 / 22,1 / 8,4 / −3,2 / 54,0 °C;
   - выбранный датчик «плывёт» на ±0,5 °C каждые 10 с (в mock-режиме цикл
     ускорен), поэтому котёл включается и выключается примерно раз в 1-1,5 минуты;
   - «Пускатель котла» повторяет состояние нагрева;
   - кнопки насоса и бойлера переключаются и запоминают состояние.

4. Автопроверка входа и API (до 16 проверок):

   ```bash
   node tools/smoke-test.js http://127.0.0.1:8080
   ```

   Пароль тест берёт из `auth.json`, `AUTH_PASSWORD` или `--password`.
   В dryRun-режиме проверяются ещё переключение бойлера и пауза насоса.
   На реальном железе без `--write` тест ничего не переключает.

5. Ручной чек-лист:

   - открыть две вкладки, переключить в одной — вторая обновится;
   - нажать «Выйти» → открывается страница входа, без пароля интерфейс и сокет
     недоступны; после входа всё возвращается;
   - насос: выключить → включить → выключить → включить подряд →
     ошибка «Слишком часто: подождите 30 с»;
   - бойлер включить → остановить сервис (`Ctrl+C`) → запустить снова:
     бойлер остаётся включённым (`state.json`);
   - через 10 с в mock-режиме (30 с на Pi) появляется `data/ГГГГММДД.csv`
     с температурами;
   - `config.txt` после запуска не меняется;
   - в логе при остановке есть `Shutdown (SIGINT)` и `OFF (остановка сервиса)`.

6. Чего локальная проверка **не** проверяет: реальные GPIO, полярность реле,
   паузу и щелчки контакторов. Это только на Pi:

   ```bash
   sudo systemctl stop pihomecontrol   # если уже стоит сервисом
   sudo node tools/relay-test.js       # силовая часть отключена!
   ```

### С телефона

Телефон и компьютер (или Pi) должны быть в одной сети. При старте сервер
печатает адреса:

```
Listening 8080 port. Открыть с телефона: Беспроводная сеть: http://192.168.0.63:8080
```

Берите адрес у Wi-Fi/Ethernet-адаптера, а не у WSL/VirtualBox/Docker.
На телефоне откройте этот адрес в браузере.

Если страница не открывается, разрешите входящие подключения (PowerShell
от администратора, Windows):

```powershell
New-NetFirewallRule -DisplayName "pihomecontrol" -Direction Inbound -Protocol TCP -LocalPort 8080 -Action Allow
```

На Pi с портом 80 адрес будет просто `http://<ip-адрес-pi>`; иногда работает
`http://raspberrypi.local`. Порт 8080 на компьютере может быть занят — возьмите
любой свободный и смотрите адрес в логе.
