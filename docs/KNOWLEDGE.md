# База знаний pihomecontrol

Живой опыт эксплуатации: что уже проверено, какие настройки трогать нельзя и
какие грабли уже собраны. Дополняйте при каждом разборе инцидента — здесь
ценнее факты с датами и командами, чем общие советы.

Связанные документы: `README.md` (как запускать и эксплуатировать),
`PLAN.md` (план доработок и что сделано).

---

## 1. Железо и пины

| BCM | Контакт гребёнки | Назначение | Режим |
|---|---|---|---|
| 4 | 7 | 1-Wire (DS18B20, 5 датчиков) | шина |
| 17 | 11 | Обратная связь пускателя котла | вход, **физически не подключён** |
| 22 | 15 | «Мощность котла» (серво) | выход, **серво по факту нет** |
| 23 | 16 | Контактор насоса (скважина) | выход |
| 24 | 18 | Контактор бойлера (ТЭН) | выход |
| 27 | 13 | Пускатель котла | выход |

- **BCM 27 — это 13-й контакт гребёнки**, а не 27-й. Физический контакт 27 —
  это BCM 0. Путаница BCM/BOARD — самая частая причина «питон включает, а
  сервис нет» и наоборот.
- Модуль реле — с оптопарой, входы активны высоким уровнем (`activeLow: false`
  у всех трёх устройств). Проверять `tools/relay-test.js`.
- У насоса и бойлера своя автоматика (реле давления, термостат) — Pi подаёт
  только питание контакторов.
- Котёл остаётся на своей 3-фазной линии; реле замыкает цепь пускателя, а
  пускает/не пускает горелку — автоматика котла.

## 2. Настройки, проверенные временем — НЕ менять «для улучшения»

Это не случайные значения, а рабочая конфигурация, прожившая 5+ лет.
Менять только по прямой просьбе владельца и с записью в разделе 7.

- `config.txt`: `1973;24;0.05;0.05;0` — гистерезис **0.05 °C**. Да, при таком
  допуске котёл переключается часто. Так работает годами, контактор и горелка
  это переносят. **Не «исправлять» на 0.3–0.5 и не добавлять `minOnSec`
  «для ресурса» без просьбы.**
- `devices.json`, насос: `"minOffSec": 30` — подобрано под реле давления,
  чтобы не дребезжать. Меньше делать нельзя.
- `devices.json`, котёл: `"restoreOnStart": false` — после рестарта котёл
  стартует выключенным, дальше его включает автоматика по температуре.
- `config/pihomecontrol.env`: `SERVO_ENABLED=0` — на этой Pi серво физически
  отсутствует, GPIO22 не трогаем.

## 3. pigpio и pigpiod: главная ловушка

**Модуль `pigpio` инициализирует библиотеку внутри процесса** (`gpioInitialise`
в `node_modules/pigpio/pigpio.js`), а не через демон. Демон `pigpiod` держит
`/var/run/pigpio.pid` — и локальная инициализация падает.

Симптом в журнале:

```
initInitialise: Can't lock /var/run/pigpio.pid
Error: pigpio error -1 in gpioInitialise
    at initializePigpio (.../node_modules/pigpio/pigpio.js:54:12)
    at new Gpio (.../node_modules/pigpio/pigpio.js:158:5)
    at Object.<anonymous> (.../homecontrol.js:26:13)
pihomecontrol.service: Scheduled restart job, restart counter is at 15
```

Последствие: сервис падает **до** создания реле и уходит в цикл перезапусков
каждые 5 секунд. В интерфейсе «нет связи», не управляется ни один контакт.
Внешне выглядит как «после перезапуска перестало работать».

Правила:

1. `pigpiod` на этой Pi **не нужен и должен быть замаскирован**:
   `sudo systemctl disable --now pigpiod && sudo systemctl mask pigpiod`.
2. Юнит не должен содержать `Wants=/After=pigpiod.service` (убрано в
   `deploy/systemd/pihomecontrol.service`).
3. Если серво нет — `SERVO_ENABLED=0`: приложение вообще не загружает `pigpio`
   и не может из-за него упасть.
4. `sudo node tools/relay-test.js` и `tools/gpio-doctor.js` запускать только
   при остановленном сервисе, иначе GPIO заняты.

## 4. Два драйвера GPIO на одном чипе — нельзя

`onoff` работает через sysfs (`/sys/class/gpio`), `pigpio` пишет регистры
SoC напрямую, мимо ядра. Когда оба живут в одном процессе на одном чипе,
состояние линии в ядре и реальный уровень пина могут разойтись: в логе `ON`,
`/sys/class/gpio/gpioN/value` = 1, а реле отпущено. Запись того же значения
становится no-op, лечит только переход 0→1.

Поэтому реле управляются **только** `onoff`, а `pigpio` — только для серво,
и лучше не держать его в процессе вовсе.

## 5. Как диагностировать

```bash
# что сервис думает и что реально на пине
journalctl -u pihomecontrol -b | grep -e "switch:" -e "Серво"
raspi-gpio get 27          # реальный уровень: level, fsel, pull
pinctrl get 27             # состояние линии в ядре
```

- `[switch:heater] ON GPIO27=1` — команда дошла, линия читается как 1. Если
  котёл не запустился, дальше ищите вне Pi: реле, его сухой контакт, катушка
  контактора, автоматика котла.
- `GPIO27=0` после записи 1 + `WARN` — выход не переключается: пин занят,
  не тот номер в `devices.json` или второй драйвер.
- `sudo node tools/gpio-doctor.js 27` — проверка тем же путём, что у сервиса:
  пишет 1/0 и читает линию обратно.
- Обратная связь `Contactor` на GPIO17 **не подключена** — её значение 0
  ничего не значит, по ней нельзя судить о контакторе.

## 6. Особенности конкретной Pi (192.168.1.68)

- Raspberry Pi 4, Raspbian 12 (bookworm), Node 22, каталог `/home/pi/pihomecontrol`.
- Сервис запускается **от root** через drop-in'ы в
  `/etc/systemd/system/pihomecontrol.service.d/`:
  `10-run-as-root.conf`, `20-root-caps.conf` (`CAP_DAC_OVERRIDE`,
  `CAP_DAC_READ_SEARCH`, `CAP_NET_BIND_SERVICE`), `30-no-pigpiod.conf`,
  `40-run-writable.conf` (`ReadWritePaths=/home/pi/pihomecontrol /run`).
  **В git этих файлов нет** — при переустановке на другой машине их нужно
  повторить. Root нужен потому, что `/sys/class/gpio` и `/home/pi` (0700)
  недоступны обычному пользователю.
- `pigpiod` — `masked`, `SERVO_ENABLED=0` в `config/pihomecontrol.env`.
- `devices.json` правится на месте и деплоем не перезаписывается
  (`tools/deploy.sh` делает `git pull --autostash`).
- `config.txt`, `state.json`, `auth.json`, `data/` — локальные, в git не входят.
- Датчики 1-Wire периодически отваливаются (`ENOENT` на `w1_slave`): 2 из 5
  живут стабильно, остальные пропадают. На управление котлом влияет только
  выбранный датчик; при трёх ошибках подряд нагрев выключается.

## 7. Журнал инцидентов

### 16.11.2026 — «реле котла не включается после перезапуска сервиса»

Что видели: сервис пишет `[switch:heater] ON`, реле втянуто, контактор не
щёлкает; `pi27.py` на том же GPIO27 включает котёл сразу.

Что выяснилось:

1. В журнале — десятки падений подряд: `pigpio error -1 in gpioInitialise`
   (раздел 3). В эти периоды сервис не управлял ничем.
2. В процессе было два драйвера GPIO (`pigpio` для серво + `onoff` для реле),
   см. раздел 4.
3. Проверка по шагам: только GPIO27 через sysfs → контактор щёлкнул и котёл
   запустился; сервис после чистого старта → тоже сработал
   (`[switch:heater] ON GPIO27=1`).
4. Обратная связь GPIO17 не подключена — по `Contactor=0` судить было нельзя.

Что сделано: `pigpio` грузится лениво и не роняет сервис
(`lib/hardware.js`, `homecontrol.js`), `SERVO_ENABLED=0`, `pigpiod` замаскирован,
юнит без зависимости от демона, установщик его останавливает; в лог пишутся
пин и прочитанное значение; добавлен `tools/gpio-doctor.js`.

Урок: «в логе ON» ≠ «реле замкнуто» ≠ «контактор замкнут» ≠ «горелка
запустилась». Проверять надо по шагам, и первый шаг — `GPIO<пин>=<уровень>`
в строке лога.

**Проверка после перезагрузки Pi (16.11.2026, 18:56).** Сервис поднялся сам
через ~2 с после загрузки: `active`, `enabled`, `NRestarts=0`. `pigpiod` не
стартовал (`masked`, pid-файла нет), в логе `Серво отключено (SERVO_ENABLED=0)`,
GPIO22 остался `input`. Через ~55 с — `[switch:heater] ON GPIO27=1`,
пин `level=1`, котёл запустился; переключение насоса из интерфейса прошло с
подтверждением `ON GPIO23=1`. Единственные ошибки в журнале — известные
`ENOENT` по отвалившимся датчикам 1-Wire.
